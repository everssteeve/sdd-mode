Cycle step 3 · /sdd spec

SPEC — the living specification

The SPEC bridges business intent and concrete implementation by AI agents. It is the agent's work instruction for a given feature — and the framework's best-ROI investment: a quality SPEC lets an agent generate more than 80% of the correct code on the first pass.

Spec as Living Invariant

SDD Mode's first founding principle positions the SPEC as a living invariant: it is not a transient document — it remains the source of truth between human intent and agent code, before, during and after implementation. Three stances exist in the spec-driven ecosystem:

Comparison of the three spec-driven stances
StanceFate of the specLimitation
Spec-firstWritten first and used for the task at hand; nothing requires keeping it afterwardsObsolete by the second iteration
Spec-as-sourceOver time, the spec becomes the main source fileRigid coupling; the real code diverges from the generator
Spec-anchored (AIAD)Kept once the task is complete, synchronized with the code at every PRRequires Drift Lock discipline

Vocabulary (doctrine v1.10). These three levels come from Birgitta Böckeler's article published on martinfowler.com on 15 October 2025. This is not a maturity scale: the article itself is reserved about the approach — long specifications that are more tedious to review than code, a sense of control that is partly illusory since agents do not always follow instructions — and spec-as-source is not an AIAD goal. "SDD" used on its own no longer says which level is meant: in an AIAD artifact, specify spec-anchored.

Traced removal of a requirement (doctrine v1.10)

A requirement never disappears from a SPEC without having been declared removed, with its reason, in the PR that removes it. In SDD Mode, this removal is guarded today by the PR review, the Anti-Drift Check and /sdd trace --fail-on-gap, which fails on an unannotated traceability gap. Known limitation: the package does not yet compare the SPEC before and after a PR, requirement by requirement; an undeclared removal can therefore slip through if traceability stays consistent. OpenSpec, for its part, has made its validation fail in that case since version 1.16.1 (November 2026): it can provide this control under AIAD (see AIAD and OpenSpec).

The argument is not merely documentary: a session anchored on a SPEC consumes on average 41.7% fewer tokens than a session without a specification (R2Code, arXiv 2026). The SPEC is a stable anchor point against context rot.

The sections of a SPEC

An AIAD SPEC is standardized. It contains twelve core sections:

  1. the activation scope — injected alone (default) or combined with other SPECs (cross-cutting features);
  2. the context — reference to the parent Intent Statement, objective, expected outcome;
  3. the scope — explicit in scope and out of scope;
  4. the impacted files — to create or modify, exhaustive list;
  5. the technical interface — endpoints, types, database schemas;
  6. the detailed behaviour — nominal flow and edge cases (at least 3 explicit edge cases);
  7. the validation rules — with schemas;
  8. the business rules to apply;
  9. the expected tests — scenarios to implement;
  10. the usage examples — concrete, request/response;
  11. the Definition of Done (DoOD) — the "Done" criteria;
  12. the Drift Criterion — the concrete rule for detecting that the SPEC has become obsolete.
**Drift Criterion**: this SPEC is in drift if the file
`auth/validator.ts` is modified without updating the
Technical Interface section.

Two sections to frame the agent (doctrine v1.9)

Doctrine v1.9 adds two sections, referred to by their label. They translate into the SPEC what the human actually delegates to the agent — see Agent autonomy.

The two SPEC sections that frame the agent
SectionStatusContent
"Agent stop points"OptionalWhen the agent must come back to a human during execution, and in what form: approval (action outside its mandate or irreversible), expert opinion (decision that goes beyond the SPEC), plurality of viewpoints (several plausible interpretations of the intent), witness (notable decision to bring to the human's attention). If the section is absent, the framework's default stop points apply.
"Agent execution scope"ConditionalRequired only if the agent holds credentials (cloud, API, SSH, database) or write access to a shared resource: isolation, allowed network egress, credentials present, shared resources with write access, intended coordination spaces, possible irreversible actions and their reversibility class. Otherwise: write "Not applicable" and fill in nothing.

A SPEC must not grow heavier with a field filled in out of ritual: outside the intended cases, the "Agent execution scope" section fits in two words. The harness permission mode does not appear in it as a containment measure — a permission mode is not a control.

In the aiad-sdd package — upcoming release, not yet published

The SPEC templates delivered by /sdd spec (prose and EARS) include these two sections in the next release of the package, not yet published; in the French templates they are labelled « Points d'arrêt de l'agent » and « Périmètre d'exécution de l'agent ». Compared with the doctrine, the template's "Agent execution scope" table adds a "Stop threshold" row — read by the Execution Gate pre-check — and has no separate "Intended coordination spaces" row.

Two more conditional sections (doctrine v1.10)

A requirement written in a SPEC is traceable; that does not make it enforced. A 2026 experiment on fairness requirements carried by the specification (three coding agents, four datasets; preprint, not peer-reviewed) measures that 97.22% of requirements are carried into the spec and 82.41% into the code, without the resulting models being significantly fairer. Doctrine v1.10 therefore adds two sections, both conditional — "Not applicable" otherwise.

The two conditional sections added by doctrine v1.10
SectionRequired only ifContent
"Critical requirements: control and failure clause"The SPEC carries at least one critical requirement: security, compliance, an action of the irreversible class, or a commitment to a third partyFor each critical requirement: the control that verifies it, its type — applied or declarative — and the failure clause: block the delivery, escalate to a named person, or accept through a traced waiver (who, when, why, until when)
"Qualified human"The SPEC touches a domain where an error directly affects a person: health, rights and legal status, finance and credit, employment, housing, education, essential services and benefitsThe person who supervises, what qualifies them in this domain, their authority (stop, modify, refuse), what they see before deciding, the trace of their decision, and how the person concerned learns that AI was used

A critical requirement without a failure clause is a wish. Any control guarding an action of the irreversible class is applied; a declarative control is only enough for the reversible class. The qualified human is not a certification: in a small team, it is the person who knows the domain and can say no. Both sections are in the doctrine's template (appendix A.4), where they are labelled « Exigences critiques : contrôle et clause d'échec » and « Humain qualifié »; they are not yet in the templates shipped by the aiad-sdd package.

Anti-pattern

The sprawling twenty-feature SPEC, or the vague "Improve performance" SPEC. Both are unusable — and cost hours of fixing the generated code, where fixing the SPEC would have taken ten minutes.

The four quality criteria

The four criteria of a quality SPEC
CriterionGood exampleBad example
AtomicityA single functional responsibility (1 SPEC = 1 PR)An entire module
Precision"Return 400 if title is empty or > 200 characters""Handle errors"
Testability"Accept test@example.com, reject invalid""Test validation"
CompletenessTypes, validation, edge cases and tests includedThe happy path alone

These four criteria feed directly into the Spec Quality Score evaluated at /sdd gate. A SPEC that does not satisfy them must never be handed to an agent. Beyond 200 lines, the SPEC is too large: head for /sdd split.

External support (doctrine v1.9)

In July 2026, Anthropic published an overhaul of its context-engineering doctrine for its Claude 5 models: removal of about 80% of Claude Code's system prompt with no measured loss according to the vendor, and a recommended shift from simple instructions towards rich, verifiable references (detailed test suites, existing code to port). This is external validation of the SQS thesis: a good SPEC is not a longer list of constraints, it is a rich and verifiable artifact. The 80% figure is the vendor's own measurement, unaudited.

The EARS variant (v1.11) — the anti-ambiguity option

Since v1.11, acceptance criteria can be written in the EARS format (Easy Approach to Requirements Syntax) via /sdd spec --ears. The SPEC is then based on the .aiad/specs/spec-ears-template.md template and declares Format : EARS in its header — that signal is what activates the strict ears-validator linter at the Gate. Each criterion follows one of five patterns:

Ubiquitous          The <system> SHALL <response>.
Event-driven        WHEN <trigger>, the <system> SHALL <response>.
State-driven        WHILE <state>, the <system> SHALL <response>.
Optional feature    WHERE <feature>, the <system> SHALL <response>.
Unwanted behaviour  IF <condition>, THEN the <system> SHALL <response>.

The linter applies rules R1–R7: forbidden words (should, might, fast, user-friendly, intuitive…), a single SHALL per criterion, an explicit trigger (WHEN/WHILE/IF/WHERE), an explicit subject, an observable verb (return, log, reject — never understand), numeric quantification ("within 200ms p95", not "quickly") and no compound conjunctions.

Effect at the Gate

0 EARS violations → guaranteed bonus of +1 on SQS criterion 2 (Testability). A single violation → criterion 2 forced to 0 and the Gate closed, with a criterion-by-criterion R1–R7 remediation plan.

EARS remains optional: the prose and EARS formats coexist, and no migration is imposed. Reserve it for SPECs where ambiguity would be costly: security, payments, regulatory compliance, public API contracts. The trade-off: roughly +30% verbosity and a learning curve.

The REASONS Canvas option (SPDD)

When the parent Intent is complex or ambiguous, /sdd spec offers the REASONS Canvas — Kevlin Henney's SPDD tool — as a framing step: it structures the justification of the intent before switching to the standard AIAD SPEC format. The two approaches are compatible: the Canvas enriches the WHY, it does not replace the SPEC format.

Splitting with /sdd split

When the Gate fails on atomicity, when the SPEC exceeds 200 lines, when the agent needs more than two re-prompts or when the context budget explodes, you split. Three patterns guide the split:

SPEC splitting patterns
PatternSplit axisExample
VerticalBy technical layer042a Backend · 042b Frontend · 042c Integration
FlowBy use case042a Happy path · 042b Edge cases · 042c Error handling
ContractInterface first, then dependencies042a Setup/contract · 042b Logic · 042c Wiring

Each sub-SPEC must be able to pass the Gate independently, and the sub-SPECs together must cover 100% of the parent. When the split yields several SPECs, /sdd spec produces a parallelism plan (waves and a dependency graph) validated by the PE before writing begins.

Warning sign

More than 5 sub-SPECs after splitting? The Intent is too ambitious: go back to /sdd intent rather than specifying a monster. Splitting is not a failure — it is a sign of Product Engineer maturity.
