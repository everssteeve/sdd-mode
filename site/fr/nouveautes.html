Nouveautés — la doctrine AIAD et le logiciel aiad-sdd

AIAD évolue selon deux cycles de versionnage distincts : la doctrine du framework (valeurs, responsabilités, artefacts, rituels, gouvernance — aujourd'hui v1.9) et le logiciel aiad-sdd (CLI, commandes slash, skills, hooks, dashboards), qui suit le versionnage SemVer de son CHANGELOG. Les deux n'avancent pas au même tempo : « v1.9 » de la doctrine et « aiad-sdd 1.9 » ne désignent pas la même chose. Cette page présente les deux fils, du plus récent au plus ancien.

Doctrine AIAD

Les évolutions de la doctrine sont publiées sur aiad.ovh. Chaque ajout est étiqueté dans le texte du framework par la version qui l'introduit.

Doctrine v1.9 (septembre 2026) — autonomie de l'agent, vérification, conformité

  • Autonomie de l'agent : continuum d'autorité en cinq niveaux (« Répondre n'est pas consentir »), points d'arrêt à l'initiative de l'agent (approbation, avis d'expert, pluralité de points de vue, témoin), classe de réversibilité et seuil d'arrêt dans le Critère de Drift de l'Intent Statement.
  • SPEC : deux sections nouvelles, « Points d'arrêt de l'agent » (optionnelle) et « Périmètre d'exécution de l'agent » (conditionnelle, dès que l'agent dispose de credentials ou d'un accès en écriture à une ressource partagée) — voir SPEC.
  • Agents Engineer : « un mode de permission n'est pas un contrôle » (la protection repose sur l'isolation) et « le confinement se juge sur la surface partagée, pas agent par agent » — voir Les 5 responsabilités.
  • Vérification : « la vérification se conçoit, elle ne s'achète pas » (quatre règles, dont la conversation critique d'abord à l'Execution Gate), exemplars de revue, Verification Tax ; côté QA, « efficacité n'est pas qualité » — voir Validation.
  • Déploiement automatisé : la confiance est une chaîne de preuve (Intent, SPEC validée à la Gate, vérifications tracées, Drift Lock) — voir Drift Lock.
  • Context Engineering Budget : budget, délégation et datation — fenêtres de 1M tokens généralisées, coût du contexte hérité par les sous-agents (déléguer tôt), toute hypothèse de capacité ou de prix datée — voir Context Engineering Budget.
  • Human Learnings : catégorie « défaillances de supervision », et question associée en rétrospective.
  • Gouvernance : calendrier AI Act recalé sur le Règlement (UE) 2026/1744 (« Omnibus numérique IA », adopté, en vigueur depuis le 27 juillet 2026), profil « Agents à effet irréversible », trace de délégation ; RGPD : décisions automatisées et agents (Art. 22 — amende infligée à Uber le 21 août 2026, dont Uber a fait appel), résidence des données du modèle selon le canal ; 4 guides Tier 1, avec l'agent CRA livré en complément par le paquet (obligation de signalement à l'ENISA en vigueur depuis le 11 septembre 2026) — voir Gouvernance.
  • Légitimation : dossiers de preuves publiés avec leurs limites (vérification, responsabilité, cas réglementaires 2026) ; validations industrielles (Tang et al. : 91,49 % de sessions nécessitant une correction humaine) — voir Valeurs & piliers.

Doctrine v1.8 — GitHub Copilot agent-native

  • Relation avec GitHub Copilot en mode « agent-native » (multi-agents en parallèle, worktrees isolés) : l'Intent Statement cadre chaque session, l'Execution Gate valide la SPEC avant chaque lancement d'agent parallèle, le Drift Lock synchronise chaque worktree avec sa SPEC.

Doctrine v1.7 (juin 2026) — vocabulaire partagé et ère des agent labs

  • Human Authorship rattaché à la « programmation agentique sérieuse » (Fowler) par opposition au vibe coding, et à la prévention de la cognitive debt ; pattern Interrogatory LLM pour /sdd intent — voir le Glossaire.
  • AIAD dans l'ère des agent labs : vide de gouvernance de l'intention, caractère model-agnostic, résistance aux disruptions de modèles.
  • Illustration de la Responsabilité Partagée par un cas d'agent doté d'autonomie financière.

Doctrine v1.6 — positionnement et Harness Engineering

  • Positionnement dans l'écosystème des outils SDD (Kiro, Spec Kit, SPDD, Symphony) ; Harness Engineering comme pratique centrale de l'Agents Engineer ; context rot et règle des 60-70 % ; appui empirique R2Code.

Doctrine v1.5 — l'intention comme artefact de premier ordre

  • Intent Statement (.aiad/intents/), Human Authorship comme 7e valeur, Test de l'Étranger (critère 6 du SQS), Human Learnings, Atelier d'Intention mensuel, Product Engineer redéfini comme gardien de l'intention, pilier « Excellence Intentionnelle » ; gouvernance réglementaire de Niveau 0 (4 guides Tier 1).

Logiciel aiad-sdd

Résumé du CHANGELOG.md officiel du paquet aiad-sdd, de la plus récente à la plus ancienne version. Chaque version est reliée aux articles du site qui documentent les fonctionnalités concernées.

Prochaine version — à paraître

Fonctions intégrées au dépôt mais pas encore publiées sur npm. Elles ne font pas partie d'aiad-sdd 1.19.0 :

  • Pré-contrôle déterministe de la Gate : aiad-sdd gate-precheck <SPEC> vérifie, hors modèle et avant le scoring SQS, la section « Périmètre d'exécution de l'agent » (action irréversible sans seuil d'arrêt, credentials ou ressources partagées sans isolation ni sorties réseau déclarées). Verdict PASS / FAIL / JNSP (exit 0 / 1 / 2) : FAIL ferme la Gate, JNSP la rend inconnue — voir CLI — gate-precheck.
  • Gabarits de SPEC : sections « Points d'arrêt de l'agent » et « Périmètre d'exécution de l'agent » dans les formats prose et EARS — voir /sdd spec.
  • Contexte hérité : /sdd context compte le contexte hérité aux points de fork des sous-agents (ligne « Contexte hérité (délégations) ») et signale les délégations tardives (contexte hérité > 50 % du total) — voir /sdd context.
  • Mise à jour sans perte : aiad-sdd update sauvegarde tout agent de gouvernance modifié localement (AIAD-X.md.bak-AAAA-MM-JJ) avant de l'écraser, grâce au manifeste .aiad-shipped.json des agents livrés — voir CLI — update.
  • Doctrine livrée : agents de gouvernance, guides et dossiers de légitimation synchronisés depuis la doctrine publiée, verrouillés par doctrine.lock.json et contrôlés en CI et avant publication.
  • Parité des commandes : les commandes livrées sont resynchronisées avec leurs copies de référence, et un contrôle de parité empêche une nouvelle divergence.

aiad-sdd 1.19.0 (30 juin 2026)

Version de consolidation : multi-runtime étendu, sobriété mesurée, pilotage produit et garde-fous outillés.

  • Kiro rejoint les runtimes de emit-rules (fichiers .kiro/steering/) — voir CLI — emit-rules ; publication d'un comparatif public qui assume forces et faiblesses.
  • Sobriété mesurée : empreinte tokens attribuée à chaque artefact et restituée dans /sdd context (aiad-sdd footprint) ; dashboard d'impact environnemental ; budgets de poids par page vérifiés en CI.
  • Dashboard PM : page « Aujourd'hui », pages détail par SPEC, hill charts, aires EBM et Investment Balance, backlog Impact × Effort, matrice outcomes ↔ Intents, inbox de triage ; data.json v2 avec JSON Schema publié — voir Métriques — dashboards.
  • Traçabilité et archivage : commande archive done (y compris SPECs découpées et FACTs résolus) ; un nouveau module sans @spec devient un gap bloquant ; squelettes de tests générés depuis une SPEC EARS (suggest-tests) — voir Traçabilité.
  • Redevabilité : FACT enrichi d'un signal de contrainte violée ; collecte automatisée des métriques DORA après déploiement.
  • Garde-fous outillés : matrice enforced / advisory (guardrails), registre catégorisé des commandes (commands), cycle de dépréciation douce, télémétrie d'usage par commande (opt-in), recommandation de modèle actionnable (/model) dans les commandes /sdd et /aiad, enchaînement automatique configurable des étapes du cycle.
  • Qualité : gates CI bloquants et badge de couverture, gate d'accessibilité WCAG 2 AA (pa11y-ci) avant publication du site, synchronisation des versions (version-sync) ; le budget de 50K tokens est requalifié en heuristique de sobriété assumée, non sourcée.

aiad-sdd 1.18 — « advisory → enforced » (juin 2026)

Release majeure : chaque règle critique du SDD devient une primitive vérifiée par le harness, et chaque verdict est calculé par un script déterministe (exit 0/1/2 + JSON validé), jamais par le jugement libre du modèle. Tout est additif et opt-in — aucune rupture.

  • Gouvernance enforced : hooks PreToolUse (JNSP, veto Tier 1 fail-closed) et Stop (Drift Lock), subagents de gouvernance read-only, veto non désactivable par un simple toggle.
  • Phase Research : verdict gradué GO | CONDITIONAL GO | DEFER | NO-GO ancré dans la Discovery, intercalé entre l'Intent et la SPEC.
  • Exécution phasée : mini-gates par tranche et troisième verdict CONDITIONAL — voir Exécution agent.
  • Mémoire, cycle, canary, observabilité : mémoire « from logs » auto-curée, cycle SDD matérialisé en graphe de tâches, suite canary anti-bruit de serving, statusLine live.
  • Garde-fous : proportionnalité, gate interactif grill-me, métadonnée d'obsolescence sunset, review cross-model additive-only.

aiad-sdd 1.15 → 1.17 (juin 2026)

Trois versions de consolidation produit (la 1.17 ne contient pas de changement utilisateur). L'essentiel :

  • Dashboard PM cockpit : des dizaines de modules de pilotage produit (couverture PRD, vélocité, OKR, Kanban role-aware, scorecards, forecast) — voir Métriques — dashboards.
  • Guide pratique SDD Mode + score de santé du backlog, commande de feedback qualitatif opt-in.
  • Trace : parsing frontmatter, cache, worker threads, mode watch, multi-langage — voir Traçabilité.
  • Assistants /sdd prd et /sdd arch + plan de parallélisme des SPECs — voir Commandes /sdd.

aiad-sdd 1.14 — fondations EU et écosystème (mai 2026)

46 items livrés pour positionner aiad-sdd comme framework européen de développement basé sur l'intention — 323 tests automatisés, zéro dépendance runtime.

  • ai-act audit : pré-remplit la documentation Annexe IV du Règlement (UE) 2024/1689 — voir AIAD-AI-ACT.
  • Packs de gouvernance par juridiction (eu-baseline, us-baseline, uk-baseline) et marketplace de packs signés SHA-256 — voir Gouvernance — packs.
  • Trace ++ : --watch, --suggest, annotations dans 13 langages, export SARIF v2.1.0, scan via git ls-files (100 000 fichiers en ~1,8 s).
  • Outillage : doctor, workspace multi-projet, REPL, migrate, télémétrie opt-in RGPD-compliant, i18n FR/EN — voir CLI npx aiad-sdd.
  • Écosystème : GitHub Action officielle, templates GitLab CI / Bitbucket / Drone, extension VS Code, site de documentation.

aiad-sdd 1.13 — dashboard HTML (mai 2026)

  • Dashboard HTML multi-pages, mode --serve et workflow GitHub Pages — voir Métriques et /aiad dashboard-html.

aiad-sdd 1.12 — multi-runtime (mai 2026)

  • aiad-sdd emit-rules fait d'AIAD la source amont des règles agent : .aiad/AGENT-GUIDE.md + gouvernance génèrent AGENTS.md, .cursor/rules/, .codex/AGENT.md et GEMINI.md — voir CLI — emit-rules. Le workflow CI aiad-emit-rules-check.yml bloque toute divergence.

aiad-sdd 1.11 — variante EARS (mai 2026)

  • Rédaction optionnelle des SPECs au format EARS (/sdd spec --ears) avec linter strict R1–R7 : 0 violation garantit +1 sur le critère SQS Testabilité — voir SPEC — variante EARS. À réserver aux SPECs où l'ambiguïté coûte cher (sécurité, paiement, conformité).

aiad-sdd 1.10 — traçabilité machine-vérifiable (avril 2026)

  • Matrice Intent ↔ SPEC ↔ Code ↔ Tests construite depuis les annotations @intent, @spec, @verified-by, @governance, générée par /sdd trace ou npx aiad-sdd trace — voir Traçabilité. La GitHub Action sdd-trace.yml fait échouer la PR sur gap bloquant.
